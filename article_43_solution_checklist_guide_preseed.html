How to read the Pre-Seed Solution checklist: what each line is actually asking

By SheBlooms 5 min read

At Pre-Seed, the solution slide isn't judged on how polished the product looks. It's judged on whether the founder is telling the truth about what exists, and whether what exists actually points back at the problem they just spent a slide describing.

The Pre-Seed solution checklist has four lines. Each one exists because founders are tempted, understandably, to present the vision instead of the build. Here's what each line is really checking, the common way founders blur the line between what's shipped and what's planned, and what a complete, honest answer looks like.

1
Screenshot or short demo included, not just a description

This line checks for evidence over assertion. A written description of a feature is unverifiable, anyone can describe a feature that doesn't exist; a screenshot or short recording is proof the thing was actually built, however early it is.

Common miss:
Including a polished Figma mockup of an upcoming redesign without labeling it as a design file, letting it imply the mockup is the live, working product.
What "done" looks like:
"Included a 40-second screen recording of Thistle's live bill-splitting flow: a user uploads a utility PDF, the app parses the amount, and splits it three ways by room size automatically."
2
Current product stage stated honestly (idea, prototype, MVP)

This line calibrates investor expectations before the meeting goes further. Calling a no-code prototype an "MVP" because it sounds more fundable buys a moment of comfort and costs trust the instant due diligence starts and the gap becomes obvious.

Common miss:
Labeling a Bubble app running on hardcoded sample data as an "MVP," when it hasn't actually processed a real transaction for a real user yet.
What "done" looks like:
"Thistle is a working prototype: three roommate households have used it for two full billing cycles, but bill parsing is still manual on our end, not yet automated."
3
Development roadmap outlined

This line checks whether the founder has thought sequentially about what comes next, not just what they'd eventually like to build. A roadmap without order or reasoning reads as a wishlist; a roadmap with sequencing reads as a plan.

Common miss:
Listing an unordered set of future features (AI chat support, a mobile app, bank integrations) with no timeline and no explanation for why each comes before or after the others.
What "done" looks like:
"Next 90 days: automate PDF parsing, currently manual. Next 6 months: launch the mobile app. Next 12 months: direct bank integrations for automatic bill pull."
4
Clear link back to the problem it solves

This line checks whether every feature shown actually traces back to the specific problem named earlier in the deck, rather than drifting toward whatever is technically interesting to build. A solution slide that impresses on its own but doesn't map to the stated problem leaves the investor doing the connecting work themselves, or not doing it at all.

Common miss:
Showcasing a feature, like an in-app roommate chat, that's technically impressive but has no connection to the specific problem (uneven utility splitting) named on the problem slide.
What "done" looks like:
"Every feature on this slide maps to the problem we opened with: unequal bill splitting. Auto-parsing removes the manual math; room-size splitting removes the argument over 'fair share.'"

Checked the box vs. actually done

Reads as checked, isn't done
  • A Figma mockup of a future redesign shown without saying it's a mockup, not the live product.
  • "MVP" used to describe a no-code prototype running on hardcoded sample data.
  • An unordered wishlist of future features with no timeline or sequencing.
  • A slick feature shown that has no connection to the problem stated earlier in the deck.
Actually done
  • A 40-second screen recording of the live bill-splitting flow, start to finish.
  • "Working prototype, used by three households for two billing cycles; parsing is still manual."
  • "Next 90 days: automate parsing. Next 6 months: mobile app. Next 12 months: bank integrations."
  • "Every feature on this slide maps directly to the unequal bill-splitting problem we opened with."

The pattern across all four: the solution slide is a trust test disguised as a product slide. Investors are watching to see whether the founder can be precise about what's real, what's planned, and why it matters, more than they're watching for polish.

A useful test

For each claim on your solution slide, ask: is this something an investor could click on right now, or is it something I'm describing as if it exists? If it's the latter, either build a rough version before the meeting or state plainly that it's on the roadmap.

Key takeaways
  • Show a screenshot or recording of the real product, never a mockup presented as if it's live.
  • Name your current stage honestly. "MVP" implies real usage, not just a working demo with sample data.
  • Sequence your roadmap; a wishlist without order reads as unplanned rather than ambitious.
  • Every feature on the slide should trace back to the specific problem you named earlier in the deck.
  • The solution slide is judged on honesty about the build, not on how impressive it looks.
